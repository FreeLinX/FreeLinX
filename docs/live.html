Live session

The live system is not unpacked into RAM. The medium carries one squashfs (boot/root.sfs, zstd). A ~300 KB initramfs — flxlive as /init plus a static sh for when it cannot go on — does the rest. It is a C program, not a script, because the userland has no switch_root, chroot or losetup.

What flxlive does

  1. Mounts proc, sys, devtmpfs itself and takes /dev/console from devtmpfs, since the initramfs has no console node of its own.
  2. Scans /sys/class/block (skipping loop and ram) for the ISO 9660 volume FREELINX_LIVE — primary descriptor at byte 32768, CD001, label at offset 40. USB sticks appear a moment after the kernel starts, so it retries for 30 seconds. Override with flx.medium=LABEL on the kernel line.
  3. Mounts the medium read-only, attaches boot/root.sfs to a loop device (read-only, no autoclear games), mounts the squashfs read-only.
  4. Mounts a tmpfs sized 75% of RAM (not the default half — installing something big like Firefox in the live session needs the room) and mounts the overlay: lower = squashfs, upper + work = tmpfs.
  5. Moves the medium to /newroot/media/flx and /dev along, then switch_root: the overlay becomes /, the system's /init takes over.

Anything that fails prints what and starts /bin/sh. RAM ends up holding the session's changes plus the page cache — about 60 MB at the start — instead of the whole system.

The medium stays reachable at /media/flx. That is where the installer and flxupgrade look for it.
